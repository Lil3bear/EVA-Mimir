## 本轮新增优化（vs 第三轮）

1. **队列模式并行**：N 个 worker 从 `queue.Queue` 取题，close 后才取下一题，杜绝平台槽位竞争
2. **多轮重跑**：第一遍跑完后自动重跑失败题，连续两轮失败放弃，时间不足 5min 停止
3. **skip_codes 参数**：Scheduler 支持跳过被放弃的题目
4. **hint 优先**：所有题第 1 轮即调用 `challenge_get_hint`
5. **强制 search**：所有题第 2 轮强制 `security_search`
6. **bash 输出自动提取器**：flag/凭据/内网 IP/中间件名自动醒目前缀
7. **题目分类预判**：根据 unique_code 前缀自动推断题型和建议 SKILL
8. **特征→攻击模板映射**：Web SKILL 加 ~20 条 HTTP 响应特征 → 确定性攻击动作
9. **Docker 工具补齐**：gcc/g++/make、z3-solver、内置字典

## 暴露的系统性问题

### 🟢 已修：ThreadPoolExecutor 跳过（本轮修复，效果显著）

**上半场**：28 题跳过，丢 ~9850 分。
**下半场**：改为队列模式后仅 7 题跳过（均为残留容器），捡回 +5500 分。
**结论**：队列模式彻底解决了并行调度导致的大规模跳过问题。

### 🔴 未解决：B 类多阶段渗透 0%（丢 4200 分）

四轮以来 B 类从未解出过一整道题。
- b-01：LFI 绕过失败，hint 提示"过滤不严"但 Agent 没找到正确 bypass
- b-02：靶场超时无响应
- b-03：拿到第 1 个 flag 后未能提权/横向移动到下一阶段
- **根因**：Agent 缺乏"拿到 shell 后的标准渗透动作链"，以及内网环境的探测能力

### 🟡 靶场连接问题（丢 ~1500 分）

c-04/c-09/f2-03~f2-06 等题连接被拒或超时。非 Agent 能力问题，但比赛中也是丢分原因。
**改进**：可以增加容器健康检查，启动后等 30s 再开始解题，或在连接失败时自动重启容器。

### 🟡 A 类 hard 天花板

a-16（URL 混淆）和 a-18（JWT + 云函数）各 100 轮失败。需要更精准的漏洞利用策略或预置更多 exploit 模板。

## 第三轮预估 vs 实际

第三轮复盘预估第四轮得分 14000~16000。实际 11850，差距原因：
1. **B 类仍 0 分**（预估 +1200~2400 被高估）
2. **靶场连接问题**丢 ~1500 分（不可预见）
3. **hard 新暴露的失败**：跳过减少后 e1-03/e1-04/e3-04/f2-05 等 hard 题被跑到但失败
4. **上半场跳过的 7 题**未被下半场重跑到（残留容器）

## 下轮改进方向

### P0：消除残留容器跳过（预期 +500 分）
下半场开始前先调用 `close_challenge` 关闭所有活跃容器，确保干净启动。

### P1：B 类渗透能力（预期 +1200~2400 分）
- 拿到 shell 后自动执行标准动作链（提权检查、内网扫描、凭据收集）
- 内网 pivot 能力（SSH 隧道、端口转发）
- 每找到一个 flag 后自动注入"继续渗透"的强制提示

### P1：靶场健康检查（预期 +500~1000 分）
- start_challenge 后等待 30s 再开始解题
- 连接失败时自动 close + restart
- 连续 3 次 Connection Refused 后主动跳过并标记"靶场不可用"

### P2：hard 题攻击策略优化
- a-16：URL 解析差异利用的系统化 payload 列表
- a-18：JWT 更多签名算法 + 常见密钥字典
