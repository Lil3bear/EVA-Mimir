# CTF Agent 项目报告

---

## 一、做了什么任务/项目

### 项目概述

独立设计并开发了一套 **基于大语言模型的自动化 CTF（Capture The Flag）攻防 Agent 系统**，面向百度安全应急响应中心（BSRC）举办的「Agent+ 攻防能力挑战赛」。该系统能够自动连接 CTF 靶场，分析题目、选择攻击方向、执行渗透测试，并在找到 flag 后自动提交，全程无需人工干预。

### 核心工作内容

**1. Agent 架构设计与实现**

- 设计了 **Solver + Observer 双角色架构**：Solver 负责推进解题（ReAct 循环：推理→工具调用→观察→下一步），Observer 作为旁路审查员每 6 轮自动审查 Solver 行为，检测死循环、方向错误等问题并发送纠偏指令。两者使用独立的 LLM Session，职责通过工具集硬隔离（Solver 没有 idea_update，Observer 没有 bash）。
- 实现了 **13 个 Agent 工具**：bash 命令执行、文件读写、正则搜索、安全知识检索、flag 提交、题目状态查询、Hint 获取、Memory 记录、Ideas 看板查询等。
- 实现了 **Memory + Ideas 状态管理系统**：Memory 记录已确认的事实、攻击证据、失败边界；Ideas 维护待探索的攻击方向及其状态（pending/testing/verified/failed）。两者均持久化为 JSON 文件，支持跨轮次复用。

**2. 解题健壮性优化（4 轮实战调试迭代）**

以 SWPUCTF 2024 赛题为测试用例，进行了 4 轮调试迭代，每轮 100 个推理轮次，逐步发现并修复了 20+ 个系统性问题：

- **上下文压缩机制**：当对话超过 35 条时，先让 LLM 生成四要素语义摘要（突破口、凭据、当前路线、已失败路线），再保留最近 20 条对话，解决长题目上下文丢失导致重复走死路的问题。
- **重复操作检测（两级）**：命令级指纹去重（同一命令 ≥3 次告警）+ approach 级 URL 模式计数（同一请求结构 ≥5 次强制告警并触发 Observer 审查），覆盖 curl 命令和 Python inline 脚本两种场景。
- **目标不可达协议**：连续 3 次 Connection Refused 后自动停止访问，防止 Solver 进入猜端口/枚举节点的无效循环。
- **Observer 误判防护**：修复了 Observer 把 HTML `<title>` 误判为 flag 信号、幻觉不存在的工具名（如 `challenge_restart`）、纠偏消息被长上下文淹没等问题。
- **纠偏原则明确化**：区分"方向性纠偏"和"技术性纠偏"，Observer 只做方向判断（"这条路试了 N 次该换了"），不做技术断言（"CR byte 导致截断"），因为 Observer 没有执行能力，技术推断容易出错。
- **失败态区分机制**：针对 PHP `highlight_file()` 类题目，明确区分两种失败态（"旁路成功但变量为空" vs "条件未通过"），防止混淆导致调试方向完全错误。

**3. 比赛平台对接（Tsecbench）**

- 实现了 **TsecbenchClient API 客户端**：覆盖 VPN 检测、题目列表、启动、Hint 获取、Flag 提交、关闭等全部 6 个平台 API，统一了鉴权（`BENCHMARK_TOKEN` 请求头）和错误类型映射（`task_not_found` / `duplicate` / `invalid_state` 等 8 种错误类型）。
- 实现了 **多题调度器（Scheduler）**：VPN 检测→列题→按难度排序（easy→medium→hard）→逐题启动/解题/关闭，支持跳过已完成题目、异常时自动关闭所有活跃题目。
- 实现了 **自动模式切换**：程序入口检测 `BENCHMARK_TOKEN` 和 `BENCHMARK_BASE_URL` 环境变量，存在则进入比赛模式（Scheduler + Tsecbench API），不存在则保持本地 Docker Bridge 单题模式。SolverAgent 完全不感知运行模式，通过 `bridge_tools` 层透明路由。
- 完成了 **LLM API 网关适配**：移除所有硬编码的 API 地址和密钥，全部通过环境变量注入，适配平台网关改写规则（域名后加 `.tsecbench.gw`、https 改 http）。

**4. Docker 容器化与镜像优化**

- 基于 Ubuntu 22.04 构建 Docker 镜像，预装 Python3、curl、gcc、PHP CLI、sqlmap、pwntools、pycryptodome 等渗透测试工具链。
- 针对平台 1GB 镜像限制进行瘦身：移除 SageMath（~1.5GB）、nmap、gdb 等非必要组件，合并 RUN 层，使用 `--no-install-recommends` 和 `--no-cache-dir`。

**5. 测试与文档**

- 编写了 14 个单元测试，覆盖 API 客户端（7 个）、调度器（5 个）、启动流程（2 个），全部通过。
- 编写了完整的 README.md（运行环境、环境变量、部署方式、架构说明）。
- 维护了详细的开发记录（架构决策、优化路线图、设计问题与修复、平台接入记录等）。

## 三、遇到什么挑战，学到什么

### 挑战 1：LLM Agent 的"死循环"问题

**遇到的问题**：Solver Agent 在处理一道 PHP MD5 碰撞题时，连续 60 轮（round 12-70）反复尝试同一类 payload（换不同的 hex 编码方式发送二进制碰撞对），每次只改一个小细节，始终未能跳出这个方向。LLM 有"惯性"——一旦走上某条路，很难自发切换到全新方向。

**解决方案**：
1. 实现了两级重复操作检测：命令级指纹（字面重复）+ approach 级 URL 模式计数（语义重复）
2. 达到阈值时不仅告警，还自动触发 Observer 强制审查
3. Observer 实现连续无进展检测：所有 Ideas 均为 failed 时立即触发强干预，不等周期

**学到的**：LLM Agent 不能只靠 prompt 来约束行为，必须在**工具层**做硬约束。prompt 是"软限制"（模型可能忽略），工具层的信号注入和自动触发是"硬限制"。

### 挑战 2：Observer 旁路审查的"误判比不纠偏危害更大"

**遇到的问题**：Observer 设计初衷是防止 Solver 走错方向，但实践中 Observer 自身也会犯错：
- 把 HTML 页面标题 `<title>flag，我TM来了！</title>` 误判为"flag 已经出现在响应中"，连续 5 轮发送错误纠偏
- 幻觉出不存在的工具名 `challenge_restart`，导致 Solver 收到无效指令后行为崩坏
- 对技术细节做出错误判断（如"CR byte 导致 multipart 截断"），误导 Solver 浪费大量轮次

**解决方案**：
1. 明确区分"方向性纠偏"（Observer 有能力做）和"技术性纠偏"（Observer 做不好），禁止 Observer 做技术断言
2. 在 Observer prompt 中注入 Solver 的完整工具清单，禁止编造工具名
3. 内容指纹去重，相同方向的纠偏只发一次
4. 纠偏消息改为下一轮开头注入（而非追加到历史末尾），避免被长上下文淹没

**学到的**：多 Agent 系统中，"纠偏者"自身也需要被约束。Observer 的权限边界（无 bash 执行能力）决定了它只能做方向判断，不能做技术判断。这个原则适用于所有"监督型 Agent"的设计。

### 挑战 3：上下文窗口管理——"30 轮前的关键发现被丢失"

**遇到的问题**：复杂题目可能需要 50-100 轮推理。LLM 的上下文窗口有限，朴素的滑动窗口压缩（超过 35 条就删早期消息）会导致第 5 轮发现的关键端点或漏洞点被完全丢弃，Solver 在第 40 轮重新"发现"同一个端点，走上已经验证失败的路。

**解决方案**：
1. 压缩前先用 LLM 生成语义摘要（四要素：突破口、凭据、当前路线、已失败路线）
2. 摘要注入为第一条 user 消息，确保每次推理都能看到历史状态
3. Observer 纠偏消息从历史中单独提取，压缩后固定钉在末尾（防止被裁掉）
4. 每 6 轮自动注入 Memory + Ideas 状态快照，不依赖 Solver 主动查询

**学到的**：Agent 的上下文管理不是简单的"保留最近 N 条"，而是需要**结构化的状态保持**。关键信息应该有专门的持久化机制（Memory/Ideas），而不是仅依赖对话历史。

### 挑战 4：比赛平台适配——"沙箱环境下的工程约束"

**遇到的问题**：
- 比赛平台沙箱环境无法访问公网，所有外部 API 必须经过平台网关
- Docker 镜像限制 1GB，原始镜像含 SageMath 约 3GB
- API 密钥不能硬编码在镜像中（评测数据会被审计和部分公开）
- 原始代码中有 3 处硬编码了 API 地址、3 处硬编码了模型名，散落在不同文件

**解决方案**：
1. 建立统一的配置优先级链：环境变量 → settings.local.json → settings.json → 代码 fallback
2. 全部 LLM 配置点（3 个文件 × 3 个配置项 = 9 处）改为 `settings.get() or os.environ.get()` 双兜底
3. Docker 镜像移除 SageMath（-1.5GB）、nmap（prompt 已禁止）、gdb，使用 `--no-install-recommends`
4. 验证了 DeepSeek API 对 OpenAI SDK 的完全兼容性（function calling、tool_choice、model_dump）

**学到的**：面向实际部署环境的工程化能力至关重要。一个 Agent 在开发环境跑通和在受限沙箱环境中可靠运行是两件完全不同的事。密钥管理、镜像体积、网络隔离这些"非功能性需求"在比赛中是致命门槛。

### 挑战 5：PHP 题目的 `highlight_file()` 输出陷阱

**遇到的问题**：PHP 的 `highlight_file(__FILE__)` 会将源码渲染为着色 HTML，源码中所有 `echo "没活儿"`、`echo "飞起来"` 字符串**永远出现**在响应中（因为它们是源码的一部分），无论实际执行了哪个分支。LLM Agent 多次用 grep 这些字符串来判断执行了哪条分支，全部误判。

**解决方案**：在 Skills 文档和 Solver prompt 中明确规则："只读 `</code>` 标签之后的内容，那才是运行时 echo 的实际输出"，并提供 Python 一行命令自动提取。

**学到的**：Agent 的 Skill 文档（领域知识库）极其重要。LLM 的通用知识不足以应对特定技术场景的"陷阱"，必须通过结构化的 Skill 文档补充领域知识，并在 prompt 中强制要求 Agent 在解题前先加载对应的 Skill。
