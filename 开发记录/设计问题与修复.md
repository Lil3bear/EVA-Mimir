# CTF Agent 设计问题与修复记录

> 基于 no-gags02 调试过程（2026-08-03）发现的系统性问题。
> 适用于所有题目，不只是 no-gags02。
> 最后更新：2026-08-03（本会话）

---

## 问题一：challenge.json 错误信息的危害远大于代码 bug

**现象**：no-gags02 的 description 里写了"array bypass 确认进入 echo $FLAG 分支"，但这是假阳性（判断方式有误）。这条错误 hint 让 Agent 误以为 `$FLAG` 变量为空是另一个独立问题，浪费了大量轮次追查 `$FLAG` 来源。

**根因**：challenge.json 的 hints/description 是 Agent 的初始上下文，优先级最高，一旦错误，后续所有推理都建立在错误基础上。

**对策**：写 challenge.json 时只记录**亲手验证过的事实**，不记录"推断"或"看起来成立"的结论。不确定的内容宁可不写，也不要写错。

---

## 问题二：security_search 会产生幻觉数值数据，Agent 不会自行验证

**现象**：Agent 调用 `security_search("PHP md5 binary collision pair")` 后，LLM 生成了若干组 hex 碰撞对，但这些 hex 在 Python 侧验证后 md5 根本不相等。Agent 没有验证就直接拿去用，浪费了十几轮。

**根因**：security_search 本质是 LLM 生成知识，对"数值类"信息（碰撞对字节、exploit 偏移量）极容易幻觉，Agent 默认相信工具返回结果。

**对策（待实施）**：
- solver.md 和 SKILL.md 对需要数值精确的操作写明"必须本地验证后再使用"
- security_search 的 tool description 加一句："返回内容为知识性参考，数值类数据需用 bash 工具在本地验证后再使用"

## 问题三：highlight_file() 输出陷阱导致结果判断完全错误

**现象**：`highlight_file(__FILE__)` 会把 PHP 源码渲染成着色 HTML，源码里所有 `echo "没活儿"`、`echo "飞起来"` 字符串**永远出现**在响应中，不管实际执行哪个分支。Agent 多次用 grep 这些字符串判断执行了哪条分支，全部误判。

**正确方法**：只读 `</code>` 标签之后的内容，那才是运行时 echo 的实际输出。

**已修复**：已在 `skills/web/SKILL.md` 第 4.1 节和 `prompts/solver.md` 的"输出截断规则"中写明。

---

## 问题四：bash_tool dedup 粒度太细，无法防止 approach-level 循环

**现象**：bash_tool 的重复检测取命令前 80 字符做指纹，Agent 每次稍微改一点 payload（不同 hex 字节、不同 boundary），指纹不同，dedup 不触发。但在"binary collision + multipart"这个层面已循环 20+ 轮。

**根因**：命令文本级别的 dedup 无法检测语义层面的循环。

**已修复**：`solver/tools/bash_tool.py` 加入 URL 模式计数器（`_approach_counter`），提取命令中 URL + 参数名结构（忽略具体值），同一结构出现 ≥5 次时输出 `⚠️ [方向循环警告]`。

---

## 问题五：Observer 工具结果截取前 300 字节，关键失败信息在末尾被丢失

**现象**：Observer 的 `on_tool_call` 回调对 result 截取了前 300 字节，而 "FAILED: isset check not passed" 这类关键诊断信息有时出现在 bash 输出的后半段，Observer 看不到，误认为操作成功，不触发纠偏。

**已修复**：`solver/observer/loop.py` 的 `on_tool_call` 方法改为取末尾 300 字节（`result[-300:]`），因为诊断信息通常在输出末尾。

---

## 问题六：Observer 幻觉不存在的 Solver 工具名（2026-08-03）

**现象**：题目实例下线（Connection Refused），Observer 发纠偏消息要求 Solver 调用 `challenge_restart` 重开实例，但该工具根本不存在。Solver 收到无效指令后行为崩坏，开始猜端口/枚举节点，浪费后续所有轮次。

**根因**：Observer system prompt 里没有 Solver 可用工具的清单。Observer 只知道"Solver 能做什么事"，不知道"Solver 有哪些具体工具名"，于是自由创造了听起来合理但不存在的工具名。

**已修复**：`solver/observer/agent.py` OBSERVER_SYSTEM_PROMPT 顶部加入 Solver 完整工具清单，并明确：**纠偏指令只能指示 Solver 使用清单内的工具，禁止编造不存在的工具名**。

---

## 问题七：Solver 无目标不可达处理协议（2026-08-03）

**现象**：题目实例下线后，Solver 没有规定行为，连续 Connection Refused 没有被识别为"实例下线"，而是被当作"换一个端口/节点试试"的信号，最终在随机猜端口上花掉剩余所有轮次。

**根因**：`solver.md` 的硬约束只禁止了 nmap 和重复 payload，没有针对"网络连接完全失败"的专门规则。

**已修复（两处）**：
1. `prompts/solver.md` 新增"目标不可达协议"：3 次 Connection Refused 后只能调 `challenge_get_state` 确认 URL，禁止猜端口。
2. `solver/tools/bash_tool.py` 新增 per-host 连续失败计数器（`_host_fail_counter`），同一 host 连续 ≥3 次连接失败时输出 `⚠️ [目标不可达]` 警告，并明确告知 Solver 下一步应调用 `challenge_get_state`。

## 问题八：两种失败态混淆，Agent 无法区分"MD5 旁路成功但 $FLAG 为空"与"传输失败"（2026-08-03 第三轮）

**现象**：leve2.php 存在两种完全不同的失败态，Agent 对其一视同仁，反复用同一方向调试：
1. `</code>` 之后 **0 字节**（空字符串）→ MD5 旁路已成功，进入了 `echo $FLAG` 分支，但 `$FLAG` 本身是空字符串
2. `</code>` 之后出现**"没活儿"** → md5(c) !== md5(d) 比较失败，传输出了问题

第三轮 100 轮日志中，round 29/45/78/96 均出现了态 1（`$FLAG` 为空），但 Agent 没有识别出这意味着旁路已经成功，继续调整 multipart 格式（应对态 2 的手段），完全绕开了真正的调查方向（`$FLAG` 来源）。

**根因**：SKILL.md 和 solver.md 都没有说明如何区分这两种失败态，Observer 的纠偏消息也没有区分。

**对策**：
- `skills/web/SKILL.md` 第 4.x 节加入"两种失败态区分方法"，明确告知 `</code>` 之后空 = 旁路成功但 `$FLAG` 为空，需调查 `$FLAG` 来源
- Observer prompt 加规则："发纠偏前先区分失败态，不同失败态对应不同调查方向，同一纠偏不能同时适用于两种失败态"

**状态**：❌ 待修复

## 问题九：`$FLAG` 来源调查路线缺失，Agent 遇到 `$FLAG` 为空时无从下手（2026-08-03 第三轮）

**现象**：Agent 进入 `echo $FLAG` 分支后输出为空，但它完全不知道应该怎么查 `$FLAG` 是在哪里定义的。`skills/web/SKILL.md` 里没有任何关于"PHP 变量从外部注入"的内容，Agent 因此在"调整 multipart 格式"和"读取 leve2.php 源码"之间徘徊，没有往 `php.ini`、`.user.ini`、`auto_prepend_file`、环境变量方向去查。

**根因**：CTF PHP 题中 `$FLAG` 通过 `auto_prepend_file` / nginx `fastcgi_param` / Docker 环境变量注入是标准套路，但 SKILL.md 完全缺失这条路线。

**对策**：
- `skills/web/SKILL.md` 新增 `$FLAG` 来源调查一节，覆盖：
  - `php://filter/read=convert.base64-encode/resource=/etc/php/7.3/fpm/php.ini` 读取 php.ini
  - `/proc/self/environ` 读取环境变量
  - `.user.ini`（当前目录、web 根目录）
  - nginx 配置 `fastcgi_param`（一般不可读，但可通过 `/proc/self/cmdline` 判断是否 fpm）

**状态**：❌ 待修复
