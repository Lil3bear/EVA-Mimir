## 根因分析

### 致命问题（导致 0 分的直接原因）

#### 1. 从未在真实环境预演过

所有之前的测试都是：
- 单元测试（mock client）
- 本地 Host Bridge 模式（Docker 内 → Linux 环境）
- API 连通性测试（只测了 HTTP 接口）

**从未做过"连 VPN → WSL 启动 → 解真实靶场题"的完整预演**。导致以下问题全部在比赛中暴露。

#### 2. `solver/platform` 命名与标准库冲突

`solver/platform/` 目录在 PYTHONPATH 包含项目根目录时，会被 `import platform` 匹配到，覆盖 Python 标准库的 `platform` 模块。`requests` 库内部调用 `platform.python_implementation()` 时崩溃。

**为什么之前没发现**：Docker 镜像中 PYTHONPATH 设为 `/opt/ctf-agent`，代码在 `/opt/ctf-agent/solver/platform/`，Python 导入时会先找标准库。而 WSL 中 PYTHONPATH 直接指向项目根目录，触发了冲突。

**修复**：`solver/platform/` → `solver/ctfplatform/`，全局替换所有 import。

#### 3. `deepseek-v4-pro` thinking 模式兼容性

从 `deepseek-chat` 切换到 `deepseek-v4-pro` 后未测试。v4-pro 是 thinking 模型，不支持 `tool_choice="required"`，返回 400。

**修复**：检测模型名含 `v4` 或 `think` 时自动改为 `tool_choice="auto"`。

#### 4. 并行调度未控制平台槽位

`ThreadPoolExecutor` 一次提交所有题目，但 `max_workers=3` 只限制线程数。3 个线程先 `start_challenge` 成功后，后续线程的 `start_challenge` 全部返回 `invalid_state: max active challenge instances reached (3)`。

**修复**：加 `threading.Semaphore(max_parallel)` 控制并发，一题完成并 `close_challenge` 后才释放槽位。

#### 5. Windows 环境不可用

Agent 的 bash 工具通过 `subprocess.run(cmd, shell=True)` 执行，在 Windows 上走 `cmd.exe`：
- `wget` / `head` / `grep` 不存在（exit code 9009）
- bash for 循环语法不兼容（"此时不应有 ep"）
- `python3` 不存在（Windows 上叫 `python`）

#### 6. Docker Desktop 网络隔离

Windows Docker Desktop 的容器网络与宿主机 OpenVPN 隧道隔离，`--network host` 在 Docker Desktop 上不等价于 Linux 上的 host 网络。容器内无法访问 `10.0.x.x` 靶场地址。
